01 Что такое GitHub Actions

GitHub Actions — встроенная в GitHub платформа автоматизации, которая позволяет запускать произвольные скрипты в ответ на события репозитория: коммиты, pull requests, релизы, расписание, вебхуки.

В отличие от Jenkins или GitLab CI, Actions полностью интегрирован с GitHub: у него есть доступ к контексту PR, issue, пакетам, реестру контейнеров, секретам и средам — без дополнительных интеграций.

03 Анатомия workflow-файла

Минимальный рабочий пример — CI для Node.js-приложения:

yaml.github/workflows/ci.yml
# Название — отображается в UI GitHub
name: CI Pipeline

# ── Триггеры ──────────────────────────────────────────
on:
  push:
    branches: [main, develop]
  pull_request:
    branches: [main]

# ── Глобальные env-переменные ────────────────────────
env:
  NODE_VERSION: '20'

# ── Jobs ─────────────────────────────────────────────
jobs:

  build-and-test:
    name: Build & Test
    runs-on: ubuntu-latest

    steps:
      # Клонировать репозиторий
      - uses: actions/checkout@v4

      # Установить Node.js (с кэшем npm)
      - name: Setup Node
        uses: actions/setup-node@v4
        with:
          node-version: ${{ env.NODE_VERSION }}
          cache: 'npm'

      - name: Install dependencies
        run: npm ci

      - name: Lint
        run: npm run lint

      - name: Test
        run: npm test -- --coverage

      - name: Upload coverage
        uses: actions/upload-artifact@v4
        with:
          name: coverage-report
          path: coverage/
          retention-days: 7
ℹ️
Совет по версиям Actions

Всегда пиннируйте Actions по SHA-коммиту в production: actions/checkout@11bd71901bbe5b1630ceea73d27597364c9af683. Это защищает от supply chain атак при компрометации тега.

04 Триггеры (on:)

Триггеры определяют, когда запускается workflow. GitHub поддерживает более 35 типов событий.

Основные события

yaml
on:

  # Push в ветку / по тегу
  push:
    branches:
      - main
      - 'release/**'       # glob-паттерн
    tags:
      - 'v*.*.*'
    paths:             # только если изменились эти файлы
      - 'src/**'
      - 'package.json'
    paths-ignore:
      - 'docs/**'
      - '*.md'

  # Pull Request
  pull_request:
    types: [opened, synchronize, reopened]

  # Расписание (cron)
  schedule:
    - cron: '0 3 * * 1-5'  # По будням в 03:00 UTC

  # Ручной запуск с параметрами
  workflow_dispatch:
    inputs:
      environment:
        description: 'Target environment'
        required: true
        type: choice
        options: [dev, staging, prod]
      dry_run:
        description: 'Dry run only'
        type: boolean
        default: false

  # Вызов из другого workflow
  workflow_call:
    inputs:
      version:
        type: string
        required: true
    secrets:
      DEPLOY_TOKEN:
        required: true

  # Событие из другого репозитория
  repository_dispatch:
    types: [deploy-prod]
⚠️
schedule и fork

Cron-триггеры не работают в форках. Если workflow не запускался 60 дней — GitHub автоматически отключает расписание.

05 Jobs, Steps и зависимости

needs: — зависимости между Jobs

По умолчанию все Jobs запускаются параллельно. Используйте needs: для последовательного выполнения и передачи outputs.

yaml
jobs:

  build:
    runs-on: ubuntu-latest
    outputs:
      image-tag: ${{ steps.meta.outputs.tags }}
    steps:
      - uses: actions/checkout@v4
      - id: meta
        uses: docker/metadata-action@v5
        with:
          images: ghcr.io/${{ github.repository }}
      - run: docker build -t ${{ steps.meta.outputs.tags }} .

  test:
    needs: build         # ждёт build
    runs-on: ubuntu-latest
    steps:
      - run: echo "Image: ${{ needs.build.outputs.image-tag }}"

  deploy-staging:
    needs: [build, test]  # ждёт оба
    runs-on: ubuntu-latest
    if: github.ref == 'refs/heads/main'
    steps:
      - run: echo "Deploying to staging..."

  notify:
    # Запускается всегда, даже если предыдущие упали
    needs: [build, test, deploy-staging]
    runs-on: ubuntu-latest
    if: always()
    steps:
      - run: echo "Status: ${{ needs.deploy-staging.result }}"

Условия if: и функции выражений

yaml
steps:
  # Только на main
  - if: github.ref == 'refs/heads/main'

  # Только при неудаче предыдущего шага
  - if: failure()

  # Всегда, даже при cancelled
  - if: always()

  # Сложное условие
  - if: |
      github.event_name == 'push' &&
      contains(github.ref, 'release') &&
      !cancelled()

  # Проверка входных данных workflow_dispatch
  - if: inputs.dry_run == false

Работа с outputs и артефактами

yaml
steps:
  - name: Generate version
    id: version
    run: |
      # Записываем output через $GITHUB_OUTPUT
      echo "tag=v$(date +%Y%m%d)-${{ github.run_number }}" >> $GITHUB_OUTPUT

  - name: Use version
    run: echo "Building ${{ steps.version.outputs.tag }}"

  # Мультистрочный output
  - name: Set matrix
    id: set-matrix
    run: |
      echo "matrix={\"include\":[{\"env\":\"dev\"},{\"env\":\"prod\"}]}" >> $GITHUB_OUTPUT

  # Summary — красивый отчёт в UI
  - name: Write summary
    run: |
      echo "## Build Results 🚀" >> $GITHUB_STEP_SUMMARY
      echo "| Status | Value |"   >> $GITHUB_STEP_SUMMARY
      echo "|--------|-------|"   >> $GITHUB_STEP_SUMMARY
      echo "| Tag | v1.2.3 |"     >> $GITHUB_STEP_SUMMARY

⚠️
Никогда не выводите секреты в echo

GitHub маскирует известные значения секретов в логах, но echo "$SECRET" | base64 или разбивка на части могут обойти маскирование. Используйте секреты только через env:.

07 Matrix builds

Matrix позволяет запускать один Job с разными комбинациями параметров — например, тестировать на нескольких версиях языка и ОС одновременно.

yaml
jobs:
  test:
    runs-on: ${{ matrix.os }}
    strategy:
      fail-fast: false   # не останавливать матрицу при первом провале
      max-parallel: 4    # не более 4 параллельных Job
      matrix:
        os:      [ubuntu-latest, windows-latest, macos-latest]
        node:    ['18', '20', '22']
        include:
          # Добавить экспериментальную комбинацию
          - os: ubuntu-latest
            node: '23'
            experimental: true
        exclude:
          # Исключить Node 18 на macOS
          - os: macos-latest
            node: '18'

    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: ${{ matrix.node }}
      - run: npm ci && npm test
        continue-on-error: ${{ matrix.experimental == true }}

Динамическая матрица из скрипта

yaml
jobs:
  prepare:
    runs-on: ubuntu-latest
    outputs:
      matrix: ${{ steps.set.outputs.matrix }}
    steps:
      - id: set
        run: |
          # Читаем сервисы из файла
          SERVICES=$(cat services.json)
          echo "matrix=$SERVICES" >> $GITHUB_OUTPUT

  deploy:
    needs: prepare
    runs-on: ubuntu-latest
    strategy:
      matrix: ${{ fromJson(needs.prepare.outputs.matrix) }}
    steps:
      - run: echo "Deploying ${{ matrix.service }}"

08 Reusable Workflows

Reusable workflows — это способ вынести общую логику в отдельный файл и вызывать его из нескольких workflow. Это DRY-принцип для CI/CD.

yaml.github/workflows/_deploy.yml  (reusable)
on:
  workflow_call:
    inputs:
      environment:
        type:     string
        required: true
      image-tag:
        type:     string
        required: true
    secrets:
      KUBE_CONFIG:
        required: true
    outputs:
      deployment-url:
        value: ${{ jobs.deploy.outputs.url }}

jobs:
  deploy:
    runs-on: ubuntu-latest
    environment: ${{ inputs.environment }}
    outputs:
      url: ${{ steps.deploy.outputs.url }}
    steps:
      - id: deploy
        run: |
          echo "Deploying ${{ inputs.image-tag }} to ${{ inputs.environment }}"
          echo "url=https://${{ inputs.environment }}.example.com" >> $GITHUB_OUTPUT
yaml.github/workflows/cd.yml  (caller)
jobs:
  deploy-staging:
    uses: ./.github/workflows/_deploy.yml
    with:
      environment: staging
      image-tag:   ${{ needs.build.outputs.image-tag }}
    secrets:
      KUBE_CONFIG: ${{ secrets.KUBE_CONFIG_STAGING }}

  deploy-prod:
    needs: deploy-staging
    uses: ./.github/workflows/_deploy.yml
    with:
      environment: production
      image-tag:   ${{ needs.build.outputs.image-tag }}
    secrets:
      inherit     # передать все секреты родителя
✅
Организация reusable workflows

Принято называть переиспользуемые файлы с подчёркивания: _build.yml, _deploy.yml. Их можно хранить в центральном репозитории .github организации и вызывать через ORG/.github/.github/workflows/_deploy.yml@main.

09 Кастомные Actions

Существует три типа кастомных Actions: JavaScript, Docker Container и Composite.

Composite Action

Наиболее простой вариант — обёртка над набором шагов. Не требует компиляции.

yamlactions/setup-python-poetry/action.yml
name: 'Setup Python + Poetry'
description: 'Installs Python, Poetry and caches dependencies'

inputs:
  python-version:
    description: 'Python version'
    required: false
    default: '3.12'
  poetry-version:
    description: 'Poetry version'
    default: '1.8.3'

outputs:
  cache-hit:
    description: 'Whether cache was hit'
    value: ${{ steps.cache.outputs.cache-hit }}

runs:
  using: "composite"
  steps:
    - uses: actions/setup-python@v5
      with:
        python-version: ${{ inputs.python-version }}

    - name: Install Poetry
      shell: bash
      run: |
        pip install poetry==${{ inputs.poetry-version }}

    - id: cache
      uses: actions/cache@v4
      with:
        path: ~/.cache/pypoetry
        key: poetry-${{ hashFiles('poetry.lock') }}

    - name: Install dependencies
      shell: bash
      run: poetry install --no-root

JavaScript Action

yamlaction.yml
name: 'Slack Notifier'
runs:
  using: 'node20'
  main: 'dist/index.js'
  pre:  'dist/pre.js'    # запускается перед main
  post: 'dist/post.js'   # запускается после main (cleanup)
javascriptsrc/index.js
const core  = require('@actions/core');
const github = require('@actions/github');

async function run() {
  try {
    const token   = core.getInput('token', { required: true });
    const message = core.getInput('message');
    const ctx     = github.context;

    core.info(`Running on: ${ctx.repo.owner}/${ctx.repo.repo}`);
    core.setOutput('result', 'success');

    // Добавить аннотацию в UI
    core.notice('Deploy completed', {
      title: 'Deployment',
      file:  'src/app.ts',
      startLine: 10
    });

  } catch (err) {
    core.setFailed(err.message);
  }
}

run();
ℹ️
Коммитить dist/ в репозиторий

JavaScript Actions должны включать dist/ в репозиторий. GitHub не устанавливает npm при использовании Action. Используйте @vercel/ncc для бандлинга всех зависимостей в один файл.

10 Environments и Deployments

Environments позволяют добавить approval gates, задержки и защиты перед деплоем в production.

yaml
jobs:
  deploy-prod:
    runs-on: ubuntu-latest
    environment:
      name: production
      url:  https://app.example.com
    concurrency:
      group:             prod-deploy
      cancel-in-progress: false  # не отменять текущий деплой
    steps:
      - run: kubectl apply -f k8s/

В настройках Environment (Settings → Environments) можно задать:

  • Required reviewers — один или несколько человек должны одобрить деплой
  • Wait timer — задержка перед запуском (до 43 200 минут = 30 дней)
  • Deployment branches — только определённые ветки могут деплоиться
  • Environment secrets — секреты, доступные только в этом Environment
  • Environment variables — переменные, специфичные для среды

11 Безопасность и OIDC

OIDC — деплой без долгоживущих ключей

OpenID Connect позволяет получать временные токены облачных провайдеров вместо хранения статических ключей в секретах.

yamlAWS через OIDC
permissions:
  id-token: write   # разрешить получение OIDC токена
  contents: read

jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - name: Configure AWS Credentials
        uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume:    arn:aws:iam::123456789:role/github-actions
          role-session-name: GitHubActions
          aws-region:        eu-west-1
          # audience — необязательно, по умолчанию sts.amazonaws.com

      - run: aws sts get-caller-identity

Минимальные permissions

yaml
# Отключить все разрешения по умолчанию
permissions: {}

jobs:
  read-only:
    permissions:
      contents:  read
      packages:  read
    runs-on: ubuntu-latest
    steps:
      - run: echo "Limited scope"

  pr-bot:
    permissions:
      contents:      read

    runs-on: ubuntu-latest

      - uses: actions/github-script@v7
        with:
          script: |
            github.rest.issues.createComment({
              issue_number: context.issue.number,
              owner: context.repo.owner,
              repo: context.repo.repo,
              body: 'Tests passed ✅'
            })

⚠️
Self-hosted + публичные репозитории = риск

Никогда не используйте self-hosted runner для публичных репозиториев без ограничений. Злоумышленник может открыть PR с вредоносным кодом, который выполнится на вашем сервере.

13 Кэширование зависимостей

yaml
steps:
  # Ручное управление кэшем
  - name: Cache node_modules
    id: cache-npm
    uses: actions/cache@v4
    with:
      path: ~/.npm
      key: npm-${{ runner.os }}-${{ hashFiles('**/package-lock.json') }}
      restore-keys: |
        npm-${{ runner.os }}-
        npm-

  - run: npm ci
    if: steps.cache-npm.outputs.cache-hit != 'true'

  # Docker layer cache с GitHub Container Registry
  - name: Build Docker image
    uses: docker/build-push-action@v6
    with:
      push: true
      tags: ghcr.io/${{ github.repository }}:latest
      cache-from: type=gha
      cache-to:   type=gha,mode=max

14 Реальные примеры

Полный CI/CD для Docker + Kubernetes

yaml.github/workflows/release.yml
name: Release

on:
  push:
    tags: ['v*.*.*']

permissions:
  contents:  write   # создание GitHub Release
  packages:  write   # push в GHCR
  id-token:  write   # OIDC для AWS

jobs:

  build:
    runs-on: ubuntu-latest
    outputs:
      image: ${{ steps.meta.outputs.tags }}
      digest: ${{ steps.push.outputs.digest }}
    steps:
      - uses: actions/checkout@v4

      - name: Docker metadata
        id: meta
        uses: docker/metadata-action@v5
        with:
          images: ghcr.io/${{ github.repository }}
          tags: |
            type=semver,pattern={{version}}
            type=semver,pattern={{major}}.{{minor}}
            type=sha

      - uses: docker/login-action@v3
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}

      - name: Build & Push
        id: push
        uses: docker/build-push-action@v6
        with:
          push:       true
          tags:       ${{ steps.meta.outputs.tags }}
          labels:     ${{ steps.meta.outputs.labels }}
          cache-from: type=gha
          cache-to:   type=gha,mode=max
          provenance: true  # SLSA provenance
          sbom:       true  # Software Bill of Materials

  deploy:
    needs: build
    runs-on: ubuntu-latest
    environment:
      name: production
      url:  https://app.example.com
    steps:
      - uses: actions/checkout@v4
      - name: AWS Credentials via OIDC
        uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: ${{ secrets.AWS_ROLE_ARN }}
          aws-region:     eu-west-1
      - run: |
          aws eks update-kubeconfig --name prod-cluster
          helm upgrade --install myapp ./chart \
            --set image.tag=${{ github.ref_name }} \
            --wait --timeout 5m

  release:
    needs: deploy
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0
      - uses: softprops/action-gh-release@v2
        with:
          generate_release_notes: true
          make_latest:           true

      - uses: actions/checkout@v4

      - name: Check PR size
        uses: actions/github-script@v7
        with:
          script: |
            const { data: pr } = await github.rest.pulls.get({
              owner:       context.repo.owner,
              repo:        context.repo.repo,
              pull_number: context.issue.number,
            });
            const lines = pr.additions + pr.deletions;
            if (lines > 500) {
              await github.rest.issues.createComment({
                issue_number: context.issue.number,
                owner: context.repo.owner,
                repo:  context.repo.repo,
                body:  `⚠️ This PR changes **${lines} lines**. Consider splitting.`
              });
            }

GitHub Actions — это не просто CI

Это полноценная платформа автоматизации, которая позволяет строить сложные multi-environment pipeline с approval gates, OIDC-аутентификацией, матричными сборками и переиспользуемой логикой. Правильная архитектура workflow — такой же код, как и основное приложение: он требует ревью, тестирования и документации.
